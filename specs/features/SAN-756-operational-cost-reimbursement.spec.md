# Operational Cost Reimbursement — Slices 1-2 (Tripura)

## Problem

Startup Tripura (T-RISE) recognizes startups and, for the 12 months following recognition, reimburses a fixed monthly operational cost sized by category — provided the startup applies for it, one month at a time. None of this exists today. This spec covers **Slices 1-2, all of Slice 3, and Slice 4**, per the authoritative BRD (`specs/features/BRD-Operational-Cost-Reimbursement-TRISE-v2.md`, Rev. 3, §14 "Suggested Slicing" + §18/§20/§21 "Amendment"), which **supersedes** the earlier client-overview docx and hour-estimate PDF used in initial scoping on every point of conflict: Slice 1 (recognition-gated visibility, eligibility-window computation, category selection with the correct fixed amount displayed — no submission yet) + Slice 2 (first-time submission: documents, bank details, self-declaration, one-claim-per-month enforcement) + **the Slice-3 download capability (single-claim AND bulk), pulled forward by explicit user directive on 2026-09-14, including the FR-8.1 transition email (BRD §18)** + **View Details (FR-6.2) and Reject-with-reason (FR-4.2, full reapply behavior), pulled forward by a second explicit user directive on 2026-09-14 (BRD §20)** + **Slice 4 (verify-and-submit for Month 2 onward, FR-5.1), now brought into scope in its own right, per the BRD's own sequencing, on 2026-09-15 (BRD §21)**. This spec also closes a gap the §20 pull-forward left open: **the Rejected-transition startup email (FR-8.1)**, which was deferred only because Reject wasn't reachable yet at the time — now that it is, this is built too (BRD §21). Everything else (Sanction, single or bulk; bulk-Sanction; the report/export section; the admin migration tool, FR-1.5) remains deferred to Slice 5 — Evidenced, BRD §14/§18/§20/§21.

**Corrections vs. earlier scoping (do not build to the old numbers):**
- Three fixed categories, not two — General ₹20,000/mo, Women-led ₹22,000/mo, **PH-led ₹24,000/mo** (confirmed by the Product Owner, not ₹25,000) — and the amount is **snapshotted onto the claim at submission time**, never a live lookup — Evidenced, BRD FR-2.1.
- **BRD FR-6.1 AC3 ("no bulk-download action exists... always single-claim") is formally amended for this feature** (BRD §18, dated 2026-09-14): bulk download is now in scope alongside single-claim download, modeled on `sc-saas-admin`'s existing bulk-download pattern.
- **The eligibility-gating field is confirmed, not open**: the user directly confirmed on 2026-09-14 ("yes manage with this recognition_generated_at") that `startups.recognition_generated_at`/`recognition_regenerated_at` is the correct field — BRD §13.1.
- **The download-triggered transition email is confirmed, not open**: the user confirmed the download-triggered Submitted→Under Process transition SHOULD fire BRD FR-8.1's "email on transition into Under Process" notification to the startup, same as any other transition into Under Process — this is now in scope for the download endpoint, reusing `SesEmailService` (`core/services/ses-email.service.ts`), the platform's existing single transactional-email mechanism (e.g. `sendProfileUnderReviewEmail`/`sendProfileRejectedByAdminEmail` are the closest existing analogs), not a new one.
- **BRD FR-1.1 is formally extended (BRD §19, dated 2026-09-14)**: an admin-configurable, per-tenant, OFF-by-default toggle ("also visible to approved startups") widens module VISIBILITY (only) to any startup with `approvalStatus === ProfileAccountStatuses.APPROVED`, even without a Recognition ID. Claim submission still unconditionally requires `recognized === true`. An approved-but-not-recognized startup let in this way sees all 12 months as locked/unclaimable (no `recognitionGeneratedAt` to anchor a real window) — a new, explicit "visible but locked" state. Implemented as a setting on the same admin-editable settings row as the self-declaration template, not a new tenants-cockpit flag.
- **View Details (FR-6.2) and Reject-with-reason (FR-4.2) are pulled forward from Slice 3 (BRD §20, dated 2026-09-14)**: an admin can open a read-only claim detail view (status timeline, claim details, bank details, document list — never changes status) and reject a claim with a required reason. Rejection is **full FR-4.2 AC5 behavior, confirmed by explicit user directive**: the month reopens, and the startup's resubmission has category and every document re-editable again. **Sanction (FR-6.5) is explicitly NOT part of this pull-forward** — stays deferred to Slice 5. This surfaces a real regression risk that must be fixed, not worked around: the code-review-added `UNIQUE(startupId, monthIndex)` constraint on `OperationalCostClaimEntity` was correct when `Rejected` was unreachable (at most one row per month could ever exist) but would now permanently block reapplication after a first rejection — see Per-repo plan (backend) for the required redesign.

## Per-repo plan

### tenants
- Add `operational_cost_reimbursement_enabled` boolean column (`width: 1, type: 'boolean', default: false`) to `TenantUsersEntity` (`sanchiconnect-saas-tenants/src/modules/tenants/entities/tenant-users.entity.ts`), following the exact pattern of the most recently added flag, `hub_spoke_domain_enabled`. Cockpit-owned per invariant #1 — no other tenants-side change needed.

### backend
- **Module placement (Practice 1 check):** the BRD (§3.1) points at `schemes-management` and `grants` as pre-existing stubs. Verified directly — both are real but genuinely empty of business logic: `SchemesController` has zero routes, `grants` is entity-only (single `amountGranted` per beneficiary, no status lifecycle, no documents, no month index). Decision: build a **new** module, `src/modules/operational-cost-reimbursement/` (mirrors `payment-management`'s controller→service→repository→entities/dto shape), reusing `SchemesEntity` as its parent scheme row (one seeded `schemes` row) rather than inventing a second grouping concept.
- **Eligibility-window algorithm:** reuse the Call-for-Applications reapplication-cooldown pattern (BRD §3.2), evidenced at `application-management/application-program.service.ts` / `program-management/program-management.service.ts` (`allowReapplication` / `reapplicationDurationType` / `getReapplyActivationDate()`), adapted to 12 fixed monthly windows anchored to `startups.recognitionGeneratedAt` (falling back to `recognitionRegeneratedAt` — confirmed gating field), with month-end-rounds-down semantics.
- Entities (TypeORM, `synchronize: true`):
  - `OperationalCostClaimEntity` — FK to `schemes.id` and `startups.id`; month index; period start/end; category (locked once set, EXCEPT unlocked again on a rejection-triggered resubmission per FR-4.2 AC5 — BRD §20); `amount` (snapshotted, integer); `status` enum (full `Submitted/UnderProcess/Sanctioned/Rejected` set — `Rejected` is now reachable per BRD §20); status timestamps per stage (nullable, `rejectedAt` now populated); `rejectionReason` (nullable free text, now populated on reject — BRD FR-4.2 AC4); `rejectedByAdminId` (nullable, for audit); `firstDownloadedAt` (nullable timestamp, write-once) and `firstDownloadedByAdminId` (nullable). Standard base shape: uuid, soft-delete, audit timestamps. **BRD §20 — one-active-claim-per-month redesign required:** replace the code-review-added blanket `@Index(['startupId','monthIndex'], {unique:true})` (which would now permanently block reapplication after any rejection) with a nullable "active slot" marker column (e.g. `activeSlot: number | null`, set to a fixed sentinel like `1` when `status` is `Submitted`/`UnderProcess`/`Sanctioned`, and explicitly set back to `null` on `Rejected`) and index `(startupId, monthIndex, activeSlot)` unique instead — MySQL/InnoDB treats each `NULL` in a unique index as distinct, so any number of `Rejected` rows coexist for the same month while at most one truly-active claim is still hard-enforced at the DB layer, not just at the application layer.
  - `OperationalCostDocumentEntity` — one row per claim's document slot, stored via the shared `UploadService`/`AmazonS3Service` (`core/upload-module/`). **Corrected (BRD §22, 2026-09-15):** the real self-declaration template already IS the shareholding-pattern declaration (one combined letterhead, not two documents) — `submitClaim()` now requires only ONE upload for this (still validated as non-empty), not a separate `shareholdingFile` + `selfDeclarationFile` pair. To stay backward-compatible with anything already reading `OperationalCostDocumentType.SHAREHOLDING` (e.g. the admin View Details document list), write TWO `OperationalCostDocumentEntity` rows from the single uploaded file — one tagged `SELF_DECLARATION`, one tagged `SHAREHOLDING`, both pointing at the SAME S3 key — rather than renaming/removing the `SHAREHOLDING` enum value (avoids touching the enum column's definition on a table that just had an unrelated index incident). The disability certificate (PH-led only) is unaffected, still its own separate upload.
  - `OperationalCostBankDetailsEntity` — one row per startup. **Extended (BRD §22, 2026-09-15):** new mandatory columns matching T-RISE's real Beneficiary Details form — `firmName`, `firmAddress`, `panNumber`, `bankName`, `bankBranchName`, `bankAccountType`, `micrCode`, `beneficiaryEmail`, `beneficiaryMobile` — alongside the existing `accountNumber`/`ifscCode`/`chequeOrPassbookImage`. **This is a purely additive column change — do NOT touch this entity's indexes, and do NOT touch `OperationalCostClaimEntity`'s unique-index/FK structure at all in this pass** (see the 2026-09-15 boot-incident history in that entity's own doc-comment) — this work is scoped to `OperationalCostBankDetailsEntity` and `OperationalCostDocumentEntity` only.
  - `OperationalCostSelfDeclarationTemplateEntity` — admin-uploaded template ref; schema owned here, written directly by `sc-saas-admin` via Medoo against the same tenant DB. **Extended (BRD §19):** also carries a `visibleToApprovedStartups` boolean (default `false`) on this same singleton settings row — a per-tenant operational toggle, not a new cockpit flag (see Contracts & invariants).
- `GET operational-cost-reimbursement/eligibility` — Slice 1 grid + category preview. **Extended (BRD §19):** visibility check becomes `startup.recognized === true` OR (`settings.visibleToApprovedStartups === true` AND `startup.approvalStatus === ProfileAccountStatuses.APPROVED`); only the first branch computes real unlock dates — the second returns all 12 months in a `locked` state (no eligible-from date, `claimable: false`), a new explicit response shape distinct from both the normal grid and the 403/404 fully-blocked response.
- `POST operational-cost-reimbursement/claims` — Slice 2 Month-1-only first-time submission. **Unaffected by BRD §19**: requires `startup.recognized === true` unconditionally, regardless of the visibility-scope setting — an approved-but-not-recognized startup that can now SEE the module still cannot submit a claim; this must be enforced server-side, not left to the frontend disabling the button.
- `GET operational-cost-reimbursement/self-declaration-template`.
- **`GET operational-cost-reimbursement/admin/claims`** — NEW, admin-authenticated: paginated list (startup name/recognition no., month, category, amount, status). Must support resolving "select all matching current filter" server-side (mirrors `sc-saas-admin`'s own `resolveBulkIds()` pattern) so bulk selection works across pagination at the expected thousands-of-startups scale.
- **`POST operational-cost-reimbursement/admin/claims/download-manifest`** — NEW, admin-authenticated. Accepts either explicit claim ids or a `{selectAll: true, filters}` instruction. For each resolved claim: (a) if `status === Submitted`, transition to `UnderProcess`, write-once-set `firstDownloadedAt`/`firstDownloadedByAdminId`, **and call a new `SesEmailService` method (e.g. `sendOperationalCostClaimUnderProcessEmail(...)`, mirroring the shape of existing per-purpose methods like `sendProfileUnderReviewEmail`/`sendProfileRejectedByAdminEmail`) to notify the startup — per BRD FR-8.1, confirmed in scope 2026-09-14**; claims already past `Submitted` are included with no side effect and no re-send (idempotent re-download, BRD FR-6.4); (b) render a fresh packet PDF via `PdfRenderHtmlService`; (c) build a manifest entry `{folder, files: [{url: pdfUrl, name}, ...documentUrls]}`. Response shape mirrors `sc-saas-admin`'s existing `get_bulk_attachment_urls` JSON shape (flat for a single claim, foldered for many) so the admin side can reuse `client-zip-downloader.js` unmodified. **Design decision (BRD §18):** one combined package per claim (PDF + that claim's documents together), not the reference precedent's separate PDF-vs-attachments dropdown options.
  - **Admin-auth note:** the exact guard for these two new admin-facing routes is an implementation-time decision — `sc-saas-admin` already calls the backend with `Authorization: Bearer <token>` for other admin-triggered actions (`sc-saas-admin/includes/core_functions.php`); mirror whatever concrete guard that pattern uses. `admin-actions.controller.ts`'s own guard shape (class-level `FeatureGuard`) is the nearest example to check first.
- **`GET operational-cost-reimbursement/admin/claims/:claimId`** — NEW, admin-authenticated (same `AdminTokenGuard` as the other two admin routes). BRD FR-6.2, View Details. Read-only — never changes status, however many times called. Returns the full status timeline (a date per stage passed through, FR-4.3), claim details (period/category/amount), bank details (account/IFSC — this is the ONE view allowed to expose them, per BRD NFR/DPDP), and the uploaded document list (names only, not signed URLs — downloading the actual files stays exclusive to the existing download-manifest endpoint, not duplicated here).
- **`POST operational-cost-reimbursement/admin/claims/:claimId/reject`** — NEW, admin-authenticated. BRD FR-4.2. Body: `{ reason: string }`, required (`@IsNotEmpty()` — reject without a reason is a 400, per FR-4.2 AC1/AC4). Sets `status = Rejected`, `rejectionReason`, `rejectedAt`, `rejectedByAdminId`, and clears the new `activeSlot` marker (see the entity redesign above) so the month is immediately reopenable. **Extended (BRD §21):** also calls a new `SesEmailService` method (e.g. `sendOperationalCostClaimRejectedEmail(...)`, mirroring `sendOperationalCostClaimUnderProcessEmail`'s shape) including the rejection reason in the email body — closing the gap §20 deliberately left open only because `Rejected` wasn't reachable at the time.
- `POST operational-cost-reimbursement/claims` (Month-1 submission, already built) — **BRD §20 note:** since `Rejected` claims no longer hold the unique slot after the entity redesign above, this endpoint's existing one-claim-per-month check (`getActiveClaimForMonth`) already correctly allows a fresh submission for a month whose only existing claim is `Rejected` — confirm this with a new test rather than assuming, and confirm the resubmission is a genuinely fresh claim row (new categories/documents, not an edit of the rejected one), matching FR-4.2 AC5's "category and all documents re-editable" via a clean new submission rather than a separate edit-in-place flow.
- **`POST operational-cost-reimbursement/claims/:monthIndex/verify-submit`** — NEW, BRD FR-5.1, Slice 4. For `monthIndex` 2-12 only (Month 1 stays exclusively on the existing first-time-submission endpoint — do not let this new endpoint also accept `monthIndex=1`). Body: only bank-details fields (`bankAccountNumber`, `bankIfscCode`, optionally a new cheque/passbook file) — no category, no document uploads. Server-side: (a) enforce the month is actually unlocked (`eligibleFrom <= now`) and has no existing active claim (reuse the same `activeSlot`-aware check as the Month-1 endpoint); (b) look up the startup's most recent claim (by `id DESC`, respecting the ordering fix from BRD §20) to carry forward `category`, `amount` (re-snapshotted at THIS submission's current category rate — confirm against FR-2.1 AC3 whether "snapshot" means the ORIGINAL first-claim amount or the category's current rate; BRD FR-5.1 doesn't explicitly re-address this for later months, so default to re-snapshotting the CURRENT rate for the selected category at this submission time, consistent with FR-2.1 AC3's stated purpose of protecting against retroactive changes to already-decided claims, and flag this default explicitly in the PR/spec rather than silently assuming — it's a genuine judgment call, not a fully-specified BRD detail) and the document entity references (point new `OperationalCostDocumentEntity` rows at the SAME underlying S3 file paths — do not re-upload or duplicate files); (c) upsert `OperationalCostBankDetailsEntity` if the bank fields changed; (d) create a new claim row for `monthIndex`, status `Submitted`, `activeSlot=1`.
- **`POST operational-cost-reimbursement/admin/claims/:claimId/sanction`** — NEW, admin-authenticated. BRD FR-6.5, single-claim form (BRD §23). Only valid when `claimStatus === UnderProcess` (409/400 otherwise — matches FR-6.1 AC1/AC2's "status only ever moves forward" and FR-6.5 AC2's "Submitted must be downloaded first" gate). Sets `claimStatus = Sanctioned`, `sanctionedAt = now()` — both existing columns, no schema change. Sends the new Sanctioned-transition email via `SesEmailService` (mirror the Rejected/Under-Process email methods' exact shape).
- **`POST operational-cost-reimbursement/admin/claims/bulk-sanction`** — NEW, admin-authenticated. BRD FR-6.5, bulk form (BRD §23). Same selection-resolution shape as `download-manifest` (explicit ids OR `{selectAll, filters}`, reusing whatever `resolveBulkIds()`-style helper that endpoint already uses). Per claim, in its own try/catch (same isolation pattern as `download-manifest`'s per-claim processing — one claim's failure must not undo another's already-committed Sanction): if `claimStatus !== UnderProcess`, record it as a per-claim failure in the response's `results` array (BRD FR-6.5 AC2 — do NOT silently skip, and do NOT Sanction it anyway) rather than a hard 400 for the whole batch; otherwise set Sanctioned + `sanctionedAt` and send the transition email. Return the same `{results: [{claimId, success, error?}]}` shape `download-manifest` already returns, so the admin can see exactly which claims in the batch succeeded/failed and why.
- Add `OPERATIONAL_COST_REIMBURSEMENT_ENABLED = 'operational_cost_reimbursement_enabled'` to `Feature` enum; gate every route with `@Features(...) @UseGuards(FeatureGuard, ...)`, mirroring `partner-branding.controller.ts`'s pattern.
