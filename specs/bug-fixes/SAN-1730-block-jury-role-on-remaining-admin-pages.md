# SAN-1730 — Block the jury role on the remaining admin pages (follow-up to SAN-1676)

**Repo:** sc-saas-admin · **Priority:** Urgent · **Class:** CODE_ERROR (missing authorization check) · **Status:** REVERTED / deferred on 2026-10-06 at the owner's request ("revert this, no need for now"). The 242 one-line additions were removed; nothing from this sweep is in the working tree. The gap below still exists.

## Problem
`index.php` has no jury route allow-list (the FA-010 gate only handles NDA signing) and `modules/common.php` only builds menus. So a jury-role session could open **any** module file whose first line was only `checkLoggedIn()`: application data, exports, imports, broadcasts, finance, developer tools, reports and more. SAN-1676 had covered 5 pages. Found by the FA-011 cross-repo review (SAN-1719). Role checks that exist on some pages (`program_manager_role_id` comparisons) are scoping logic that narrows a programme manager's view; any other role, including a jury session, is not narrowed. So pattern-matching on "has a role check" is not a safe way to decide which pages are already protected.

## Rule used
Every routable module that calls `checkLoggedIn();` and has **no explicit jury handling** (`jury_role_id`, `denyJuryRoleAccess`, `juryNdaGateIsJurySession`, `is_jury_reviewer`) gets `denyJuryRoleAccess();` on the line right after it (redirect to `/jury/dashboard` on a page load, 403 JSON on POST/AJAX), except the pages jurors legitimately use.

## Fix
- 242 module files, one added line each (appendix below).
- 116 files already had explicit jury handling: untouched.
- **Left alone on purpose (jurors use them):** `jury/*` (all jury pages, including `jury/nda.php`), `auth/jury.php`, `auth/profile.php` (the jury header links to profile and logout), `403.php`, `404.php`. `index.php`, `index1.php`, `dashboards.php`, `direct-access.php`, `iframe_loader.php` do not call `checkLoggedIn();` or already handle jury, so they were not touched.
- **Left alone, intentionally public pages (their `checkLoggedIn()` is commented out, so there is no login at all):** `email_template_preview.php`, `form_builder/public_submissions.php`, `meetings/detail.php`, `meetings/detail_backup.php`, `meetings/session_detail.php`. This is a separate question (should these be public?), not a jury issue.
- `scrapper/iesa_scrapper.php` has no database access, API call or file work, so it was not in the active set and was not changed.
- Evidence for the jury keep-list: the jury header and templates link only to `jury/*`, `auth/profile` and `auth/logout`; none of the jury-reachable pages call `ajax/*`, `upload/*`, `aws/*`, `notifications/*` or `filemanager/*`; no jury module includes any of the 242 files.

## Verification
- `php -l` clean on all 242 files; each changed by exactly one added line (the one file with more, `system_logs/list.php`, also carries the earlier FA-011 System Logs change).
- The denial is on the line right after `checkLoggedIn();` in every file; only comments and a `use` statement precede it in the files where it is further down.
- The helper itself: admin passes through, a jury session is redirected on GET, gets `403 {"success":0,"message":"Access denied."}` on POST, and a session carrying only `admin_role_code` is also blocked (CLI check).
- **Not done:** a real jury login on staging. Please check that a jury user can still open: dashboard, a round and an application, the NDA pop-up, profile and logout. Automated test coverage was not added (sc-saas-admin has no test framework).
