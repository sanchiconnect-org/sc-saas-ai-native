Implement a feature spec, given its id.
1. Read specs/features/<id>-*.spec.md. Refuse unless status is `approved`; if `draft`, summarize what needs sign-off and stop.
2. Read the module spec(s) for modules you'll touch and each affected repo's CLAUDE.md.
3. Find the spec's Linear issues: `list_issues` with `project` = the spec's `linear:` project, keeping only those whose `projectMilestone` is the spec's `linear_milestone:` (SAN-1579: specs are milestones inside a project). An older spec with no `linear_milestone:` owns its whole project, so take every issue there. Before starting a repo's section of the per-repo plan, move that repo's issue to In Progress. This and every other Linear state-transition call in this workflow (steps 3, 7, 8) must set `state` ONLY — never pass `labels`, `priority`, or `assignee` on these calls, since `labels` replaces the full label set and would silently wipe the repo badge/type label spec-author already set. Those three fields are set once by spec-author and must never be touched again here.
4. Work the per-repo plan in order. Don't start a downstream repo until the upstream contract is in place. Refuse to start if any `depends_on` spec is not `done`. Use branch `<id>-<slug>` in each repo. **Enforce single-repo scope per issue**: while a given repo's issue is In Progress, only edit files in that one repo. If implementing it reveals a change is genuinely needed in a repo that isn't already its own line item in the per-repo plan, stop — do not edit that other repo under the current issue. Instead, update the spec's per-repo plan to add it (or, if that's a bigger change than expected, pause and get the spec re-approved), then create a new Linear issue for that repo (same project and same milestone, labeled/prioritized/assigned per spec-author's step 7) before touching it.
5. Honor the contracts block; if you need more, STOP and update the spec for re-approval.
6. For each repo whose changes have a real test framework (NestJS/Jest, Angular, pytest — skip the PHP repos, which have none), generate spec-traceable tests: bind assertions to the actual code symbols you just wrote (never a hallucinated API), derive expected behavior from the spec's acceptance criteria only (never from re-reading your own implementation as if it were the oracle), and cover at minimum boundary values, null/empty/missing input, and error paths alongside the happy path.
7. Before status `in-review`, run as gates: api-contract-auditor (if contracts.api non-empty); feature-flag-mapper (each flag); tenant-isolation-reviewer (if tenant_scoped). Fix all findings. If the change is behavior-risky (touches an existing live flow, not purely additive), prefer landing it behind a feature flag defaulted off, flipped on after a smoke check — call this out in the spec's Rollout section if it isn't already. Move each repo's Linear issue to In Review once its gates pass, posting the handover note from `specs/handover-note.md` on it at the same time (**Changed** with commit sha and branch, **Verified** with the gate commands and their pasted output, **Open**). No In Review move without the note.
8. Update a touched module's module.spec.md in the same change. Update the spec's `status`, and move each repo's Linear issue to Done once merged. Use the Sanchiconnect team's real states only (Backlog/Todo/In Progress/In Review/Done/Canceled/Duplicate) — never invent new state names.
Never weaken tenant scoping. Never commit secrets. Stay within scope.
