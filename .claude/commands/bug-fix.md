---
description: Fix a bug (or ship a small, self-contained enhancement) with lightweight Linear tracking — no spec ceremony.
argument-hint: <short description of the bug/enhancement>
---
$ARGUMENTS

1. Create a Linear issue in the Sanchiconnect team backlog (no project — this is flat, single-issue tracking) titled from the description, state Todo. Always set, on the same `save_issue` call:
   - `labels`: `["Bug", "<Repo label>"]` (or `"Improvement"` instead of `"Bug"` if this is a small enhancement rather than a defect). Pick the repo label(s) from: `Repo: Tenants` (sanchiconnect-saas-tenants), `Repo: Backend` (sc-saas-backend), `Repo: Frontend` (sc-saas-frontend), `Repo: Admin` (sc-saas-admin), `Repo: AI Analyzer` (ai-startups-analyzer), `Repo: 3rdparty Webservices` (sc-saas-3rdparty-webservices), `Repo: Tenants-Admin` (sanchiconnect-saas-tenants-admin). If the bug is confirmed multi-repo (see step 2), file one issue per repo instead of one issue with multiple repo labels.
   - `priority`: 1 (Urgent) for security/data-loss/production-breaking; 2 (High) for a broken or blocked workflow; 3 (Medium) for wrong-but-workaroundable behavior (the default when unsure); 4 (Low) for cosmetic/minor issues. Never leave this unset.
   - `assignee`: **ask the user who this should be assigned to before creating the issue** — revised 2026-08-13, this is no longer a fixed repo→developer lookup. Judge whether the fix is a single-repo or multi-repo task; if multi-repo (one issue per repo, per the labels note above), the same single named assignee goes on every one of those issues, not a different person per repo.

   Move it to In Progress before starting work.
2. Investigate and fix directly in the affected repo(s) — no spec file required for a narrowly-scoped, single-repo change. **Enforce single-repo scope**: if it turns out the fix needs changes in a repo other than the one this issue is labeled for, do not edit that other repo under this issue. Instead, finish only the current repo's piece (or stop here if the current repo isn't the right place to start), then either file a second flat bug-fix issue in the other repo (same steps above, correctly labeled/prioritized/assigned for that repo) or, if the scope has grown into real design/acceptance-criteria work, stop and suggest `/spec-new` instead — don't keep going as a bug fix, and don't silently touch a repo this issue isn't labeled for.
2a. Before writing a fix, classify the failure as one of: **CODE_ERROR** (the code doesn't do what it's supposed to — the common case), **SPEC_ERROR** (the code does what was asked, but the requirement/expectation itself was wrong or ambiguous — flag this back to the user rather than silently "fixing" intended behavior), or **ENV_ERROR** (config, environment, or a third-party dependency, not the code). Only proceed straight to a code fix for CODE_ERROR; for the other two, say so explicitly before touching anything.
3. If the fix was a CODE_ERROR and lands in a repo with a working test framework (`sanchiconnect-saas-tenants`, `sc-saas-backend`, `sc-saas-3rdparty-webservices` — NestJS/Jest; `sc-saas-frontend` — Angular), propose a regression test covering this specific bug — say what it will assert and which file it goes in — and **wait for the user's go-ahead before writing it**. Do not write the test until confirmed. Skip this step (and say so) for `sc-saas-admin` and `sanchiconnect-saas-tenants-admin` (no test framework exists) and `ai-startups-analyzer` (no test suite set up yet) — note the gap rather than bootstrapping test infrastructure as a side effect of a bug fix.
4. Run the affected repo's own lint/check (`php -l`, `npm run lint`, `tsc --noEmit`, etc.) on every touched file, including any new test file.
5. Once the fix is ready, add a comment to the Linear issue with the root cause, followed by the handover note in the exact shape of `specs/handover-note.md` (**Changed** with commit sha and branch, **Verified** with the commands and their pasted output, **Open**), and move it to In Review (or Done, only if the user has you commit/merge directly). Use the Sanchiconnect team's real states only (Backlog/Todo/In Progress/In Review/Done/Canceled/Duplicate).
6. Also write a local record to `specs/bug-fixes/<id>-<slug>.md` (create the folder if it doesn't exist yet) mirroring the Linear issue: problem, evidence, root cause, fix (files changed), verification, and the commit hash once committed. Keep it as lightweight as the Linear issue itself — this is not a feature spec, no template ceremony required, just enough for someone to find the story of this bug without digging through Linear.
